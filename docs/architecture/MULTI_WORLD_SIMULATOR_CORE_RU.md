# Ядро симулятора с несколькими мирами

## Назначение

Версия v15.5 отделяет **симулятор** от конкретной карты. Раньше `LunarApp` и
`PlanetaryApp` одновременно отвечали за загрузку мира, управление, меню,
горячие клавиши и диагностику. При добавлении новой сцены это приводило бы к
копированию кода и постепенному расхождению поведения.

Теперь точкой входа является единый `SimulatorApp`:

```text
main.tscn
└── SimulatorApp
    ├── WorldCatalog
    ├── CommandRegistry
    ├── RuntimeTestRegistry
    ├── DeveloperConsole
    └── WorldHost
        └── ActiveWorldRuntime
            ├── LunarApp
            ├── EarthApp
            ├── PlanetaryApp
            ├── ItemSystemLab
            └── PlaygroundRuntime
```

## Ответственность слоёв

### SimulatorApp

`scripts/app/simulator_app.gd` владеет только общими механизмами:

- читает каталог миров;
- создаёт и выгружает активный runtime;
- хранит историю переходов между мирами;
- предоставляет единый реестр команд;
- показывает общую консоль;
- предоставляет общий реестр runtime-тестов;
- обрабатывает минимальный набор глобальных клавиш;
- поддерживает запуск мира и тестов из командной строки.

Он не знает, как устроена поверхность Луны, атмосфера Земли, предметный домен
или конкретный контроллер персонажа.

### World Runtime

Каждый мир является подключаемым runtime-модулем. Он получает контекст ядра,
регистрирует только свои команды и тесты, а перед выгрузкой освобождает ресурсы.
Различия миров выражаются данными и командами, а не отдельными копиями
симулятора.

### WorldCatalog

`config/worlds/catalog.json` — единственный список доступных миров. Описание
содержит идентификатор, название, тип загрузки, путь к скрипту или сцене,
параметры и теги.

Начальный набор:

| ID | Назначение |
|---|---|
| `moon` | только Луна |
| `earth` | отдельный `EarthApp`, в каталоге тел только Земля |
| `earth_moon` | `PlanetaryApp`, Земля и Луна в общем пространстве |
| `item_lab` | изолированная лаборатория предметов и контейнеров |
| `playground` | небольшая закрытая площадка с персонажем |

## Почему управление не расходится

Контроллеры персонажа по-прежнему подключаются через `ControllerHost` и общий
контракт профиля. Мир не реализует собственный вариант WASD, мыши или камеры.
Лунный runtime использует существующие EVA/Jetpack-профили, а плоская тестовая
площадка — новый `flat_humanoid` профиль через тот же хост.

Глобальные клавиши ограничены:

```text
~        открыть/закрыть консоль
F1       показать справку
Tab      освободить/захватить мышь
E        выполнить стандартное действие interact, если оно доступно
```

Общие movement actions задаются ядром один раз: `WASD`, `Space`, `Ctrl`,
`Shift`, `Q/R` и `H`. Карта выбирает профиль контроллера, но не переписывает
эти actions. Команда `input.bindings` показывает актуальный минимальный набор.

Остальная функциональность доступна командами. `display.fullscreen.toggle` и
`display.resolution.cycle` также принадлежат ядру и доступны в любой карте.
Старые клавиши сохранены как совместимый слой при автономном запуске старого
runtime, но при работе под `SimulatorApp` не обрабатываются. Это предотвращает
двойное выполнение.

## Универсальная командная система

`CommandRegistry` хранит описание, usage, aliases, категорию, владельца и
`Callable`. Владелец `core` живёт всё время, владелец `active_world` удаляется
при смене мира.

Примеры:

```text
help
world.list
world.load moon
world.load earth
world.load earth_moon
world.load item_lab
world.load playground
world.back
display.fullscreen.toggle
display.resolution.cycle
runtime.snapshot
test.list
test.run all
```

Команды конкретного мира появляются только тогда, когда соответствующий runtime
загружен. Например, лунные команды не остаются ни в `earth`, ни в лаборатории
предметов. Матрица запуска проверяет одновременно обязательные и запрещённые ID,
а Earth smoke-тест проверяет, что каталог небесных тел равен только `earth`.
Реестры фиксируют конфликты ID/aliases; при ошибке регистрации candidate runtime
полностью удаляется и не остаётся в частично активном состоянии.

Парсер поддерживает:

- одинарные и двойные кавычки;
- экранирование пробела и специальных символов;
- алиасы;
- автодополнение по Tab;
- историю команд по Up/Down.

## Жизненный цикл смены мира

```text
запрос world.load
→ проверка записи в каталоге
→ создание script или scene runtime
→ проверка WORLD_RUNTIME_V1
→ prepare_for_unload() старого runtime
→ удаление команд и тестов owner=active_world
→ queue_free старого runtime
→ configure_runtime(context)
→ добавление в WorldHost
→ регистрация команд и тестов
→ проверка коллизий и наличия smoke-тестов
→ готовый активный мир либо полная отмена candidate runtime
```

Контекст содержит ссылки на ядро, командный реестр, тестовый реестр, ID мира,
его полное описание и options. Runtime не ищет глобальные singleton-узлы.

## Различия интерфейса между мирами

Меню конкретной карты больше не является навигационным центром. Общие действия
обязаны быть командами ядра. Специализированный HUD допустим только как
представление состояния мира и как кнопки-вызовы зарегистрированных команд.
Большие диагностические панели не открываются автоматически внутри
`SimulatorApp`: они являются необязательным представлением поверх команд, а не
вторым способом управления конкретной картой.

Правило:

> Если действие должно быть доступно более чем в одном мире, его ID и смысл
> принадлежат ядру или общему сервису. Мир может предоставить реализацию, но не
> создавать несовместимую копию команды.

## Тестирование внутри движка

Есть два уровня:

1. **Статические/headless-тесты** — запускают реестры, каталог и загрузочную
   матрицу без ручного ввода.
2. **Runtime-тесты** — регистрируются активным миром и запускаются через
   `test.run <id>` или `test.run all` прямо в игровой консоли.

Командная строка Godot:

```text
--world=moon
--world=playground
--run-tests=all
--world=item_lab --run-tests=all
```

Аргументы передаются после `--`, если используется стандартный исполняемый файл
Godot.

## Добавление нового мира

1. Создать runtime-скрипт или сцену.
2. Реализовать контракт `WORLD_RUNTIME_V1`.
3. Добавить запись в `config/worlds/catalog.json`.
4. Зарегистрировать команды с владельцем, переданным ядром.
5. Зарегистрировать минимум один smoke-тест.
6. Добавить ID, обязательные и запрещённые команды в boot matrix.
7. Обновить документацию и критерии приёмки.

Профили контроллеров используют схему
`planet_simulator.controller_profile.v1`; loader временно принимает и legacy
`lunar.controller_profile.v1`, чтобы миграция не ломала существующие миры.

Код `SimulatorApp`, консоли и существующих миров при этом не изменяется.

## Следующее расширение ядра

После стабилизации v15.5:

- вынести ввод в декларативные command bindings;
- добавить разрешения команд (`player`, `developer`, `automation`);
- добавить командные сценарии `.simtest`;
- сохранять результаты тестов в JSON/JUnit;
- отделить persistent world identity от записи каталога запуска;
- добавить загрузку пользовательских world packs без изменения проекта.
