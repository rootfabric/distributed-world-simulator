# Целевая архитектура лунного симулятора

## Назначение

Цель проекта — создать единую цифровую Луну, в которой могут одновременно
существовать:

- игроки и операторы;
- автономные роботы;
- наземные базы;
- шахты и тоннели;
- пещеры;
- посадочные площадки;
- транспортные маршруты;
- научные эксперименты;
- цифровые двойники реальных роботов.

Мир должен оставаться логически непрерывным, но не обязан симулироваться целиком
с одинаковой точностью.

## Главный принцип

> Луна одна, а активных точек симуляции может быть много.

```text
Логически единая Луна
        │
        ├── участок базы
        ├── участок шахты
        ├── экспедиция
        ├── пещерная система
        └── удалённый фоновой участок
```

Неактивная территория существует как детерминированный рельеф и сохранённые
данные. Полная физика включается только в активных областях.

## Слои системы

```text
Application
    управление приложением, режимы запуска, настройки

Presentation
    HUD, диагностика, редакторы, визуализация

Actors
    игрок, спектатор, роботы, транспорт

World
    координаты, зоны, чанки, LOD, рельеф, материалы

Simulation
    сущности, физика, ресурсы, строительство, миссии

Persistence
    snapshots, terrain deltas, entity state

Integration — позже
    Robot Agent, ROS 2, RMF, сетевые сервисы
```

## Разделение визуализации и симуляции

Визуальный LOD отвечает за картинку:

```text
GLOBAL → REGIONAL → LOCAL → ULTRA
```

Симуляционное разбиение отвечает за владение данными:

```text
Cube Face → Zone → Chunk → Entity
```

Это независимые системы. Один непрерывный визуальный меш может пересекать
несколько симуляционных чанков. Такое разделение предотвращает трещины в
геометрии и позволяет менять серверное разбиение без перестройки графики.

## Координаты

Используются три уровня:

1. **Moon-fixed double position** — абсолютная позиция относительно центра Луны.
2. **Zone/Chunk address** — устойчивый дискретный адрес данных.
3. **Camera-relative local position** — координаты рядом с нулём для Godot и GPU.

## Сущности

Любой постоянный объект должен иметь неизменный `entity_id` и набор компонентов:

```text
Entity
├── transform
├── zone/chunk address
├── mobility
├── power
├── inventory
├── health
├── construction
├── robot agent
└── sensors
```

В каждый момент времени сущность имеет одного авторитетного владельца. Пока это
локальный процесс. В будущем владельцем станет Site/Zone Server.

## Рельеф

Целевая модель гибридная:

```text
Глобальная поверхность
    spherical heightfield / clipmap

Локальные изменения
    sparse terrain delta chunks

Тоннели и пещеры
    voxel или SDF chunks

Интерьеры базы
    модульная scene geometry
```

Heightfield остаётся эффективным для всей Луны. Voxel/SDF включается только там,
где появились тоннели, навесы или пещеры.

## Уровни активности

- **Dormant** — только сохранённые данные.
- **Warm** — данные загружены, физика не выполняется.
- **Active** — локальная физика, роботы и взаимодействия.
- **Laboratory** — повышенная точность датчиков и динамики для эксперимента.

Текущая v11 реализует `Warm` и `Active` для логических зон и чанков в одном
процессе.

## Несколько баз

Каждая база в будущем становится `Site`, состоящим из нескольких зон:

```text
Site: Shackleton Alpha
├── surface zone
├── landing zone
├── habitat zone
├── mining zone
└── tunnel zone
```

Удалённые базы не обязаны находиться в одной физической сцене. Их связывает
единая система координат, глобальные идентификаторы, миссии и сохранённое
состояние.

## Масштабирование

Путь масштабирования должен быть последовательным:

```text
один процесс
→ несколько локальных Site Runtime
→ отдельные процессы
→ отдельные серверы зон
→ динамическое распределение зон
```

Ни один модуль текущего проекта не должен напрямую зависеть от Kubernetes,
NATS или конкретного сетевого протокола. Сначала стабилизируются локальные
контракты.
