# ADR-002: универсальная cube-sphere адресация поверхностей

**Статус:** принято и зафиксировано  
**Версия решения:** v15.5.1  
**Предыдущее решение:** лунная cube-sphere адресация v11

## Контекст

Широта/долгота создаёт сходимость ячеек у полюсов и неудобна для равномерного
разделения симуляционной нагрузки. Одновременно координатная сетка не может
оставаться частью `LunarZoneManager`: Земля, Луна и будущие тела должны
использовать один алгоритм с разными параметрами, а изменение параметров не
должно переиспользовать старые адреса и файлы.

## Решение

Использовать общий модуль:

```text
scripts/simulation/partition/cube_sphere_grid.gd
```

Каждая поверхность задаёт неизменяемый для одной revision дескриптор:

```text
scheme_id
scheme_revision
body_frame_id
body_radius_m
zones_per_face
chunks_per_zone
```

Канонический адрес содержит namespace Вселенной, экземпляра, пространства,
схему и её revision:

```text
universe/main/instance/persistent/space/moon/
partition/cube_sphere/revision/1/zone/f4/17/09/chunk/03/28
```

Переходы через рёбра и углы граней выполняются топологически через направление
на cube-sphere, а не метрическим смещением приблизительной касательной и не
простым сложением индексов.

## Инварианты

1. `body_frame_id` указывает frame, в котором разрешено вычислять адрес.
2. Одинаковые индексы Земли и Луны имеют разные IDs из-за `space_id`.
3. Параллельные сценарии имеют разные IDs из-за `instance_id`.
4. Любое несовместимое изменение сетки требует новой `scheme_revision`.
5. Revision входит в ID и путь persistence (`cube_sphere_r1`).
6. Manifest хранит полный дескриптор сетки и отклоняет изменённую плотность под
   прежней revision.
7. Неверная конфигурация не заменяется значениями по умолчанию: инициализация
   partition runtime завершается ошибкой.
8. Render LOD, reference frame, partition address и authority owner остаются
   независимыми понятиями.

## Миграция

Локальный file storage читает:

- исходные `zones/...` файлы;
- ранние namespaced пути без `instance_id`;
- пути `cube_sphere_v1` с instance;
- текущие пути `cube_sphere_r1`.

После успешного сохранения создаётся текущий файл, а устаревшие копии удаляются.
При удалении последней сущности очищаются все варианты пути, чтобы старый файл
не мог восстановить уже удалённую сущность.

## Последствия

- отсутствует отдельная полярная зона;
- адрес компактен, детерминирован и пригоден для серверного шардинга;
- одна реализация обслуживает тела разного радиуса и плотности сетки;
- границы граней не создают разрывов interest window;
- смена параметров сетки становится явной миграцией, а не скрытой порчей данных;
- геометрическая площадь ячеек остаётся неидеально равномерной, что приемлемо
  для simulation partition, но должно учитываться балансировщиком нагрузки.
