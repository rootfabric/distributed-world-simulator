# Container State v2

## Назначение

`planet_simulator.container_state.v2` описывает как физические контейнеры, так и логические контейнеры актёра. Контейнер хранит только ссылки на `ItemInstance`; сам предмет остаётся единственным авторитетным aggregate.

## Режимы хранения

### BULK

Предмет можно поместить без фиксированной позиции. Ограничения задаются количеством логических мест, массой, объёмом, разрешением вложенных контейнеров, тегами и definition ID. Этот режим подходит для рюкзака, грузового ящика и трюма Space Engineers-типа.

### SLOTS

Каждый предмет занимает конкретный индекс. У слота может быть собственное правило:

```json
{"accepted_tags":["battery"],"accepted_definition_ids":[]}
```

Так моделируются батарейные шкафы, toolbelt, equipment sockets и десять быстрых слотов игрока. `slot_assignments` и `ItemRelation.slot_index` обязаны совпадать.

## Иерархия

`parent_container_id` позволяет сделать hotbar дочерней частью рюкзака. Его содержимое учитывается в общей рекурсивной массе, но остаётся отдельной UI-зоной и набором фиксированных слотов.

Циклы parent-container запрещены и блокируют загрузку всего item graph.

## Ёмкость

`maximum_mass_kg` и `maximum_volume_l` поддерживают неограниченное значение в runtime. В JSON бесконечность кодируется конечным маркером `-1.0`, чтобы snapshot оставался стандартным и переносимым.

## Инварианты

- один item ID встречается максимум в одном контейнере;
- relation предмета и membership контейнера совпадают;
- слот находится в диапазоне;
- один слот содержит максимум один stack;
- definition предмета удовлетворяет правилам слота;
- контейнер-предмет имеет двустороннюю owner-ссылку;
- вложенность не превышает configured depth.

## Контракт стеков v16.1

Совместимость стека определяется `ItemInstance.is_stack_compatible()`:

- одинаковый `definition_id`;
- одинаковый `display_name`;
- одинаковые component payload;
- предмет не владеет вложенным контейнером;
- итоговое количество не превышает `ItemDefinition.max_stack`.

Поведение зависит от режима хранения.

### BULK

`BULK` не имеет фиксированных пользовательских ячеек. `slot_count` в этом режиме ограничивает число отдельных stack entries и используется UI как визуальная ёмкость, но не задаёт адрес предмета.

При переносе в BULK система:

1. проходит по совместимым существующим стакам;
2. заполняет каждый до `max_stack`;
3. удаляет полностью поглощённый source aggregate;
4. помещает непоглощённый остаток отдельным stack entry;
5. отклоняет операцию до мутации, если distinct-entry limit заполнен и суммарной свободной ёмкости совместимых стаков недостаточно.

### SLOTS

В `SLOTS` поведение определяется конкретной целевой ячейкой:

- перенос на занятую совместимую ячейку объединяет количество;
- если целевой стак заполняется, непоместившийся остаток остаётся в исходной ячейке;
- перенос на пустую ячейку создаёт отдельный стак и не ищет совместимые стаки в соседних ячейках;
- несовместимая занятая ячейка возвращает `SLOT_OCCUPIED`;
- заполненный совместимый стак возвращает `SLOT_STACK_FULL` на UI-уровне.

ПКМ в inventory UI выбирает количество следующего drag-and-drop. Сам перенос всё равно выполняется через `ItemTransferService`, revision guard и operation ledger.
