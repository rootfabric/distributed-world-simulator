# P7 post-acceptance R1: исправление блокировок и контрольного пакета

База: `438b21d0f5f348d838c2fae0bfae3547ba56a875`.
Work Order: `V0-P7-POST-ACCEPTANCE-REPAIR-R1`.
Это кандидат исправления, не новая acceptance и не активация MVP.

## Владелец и доказанная причина

Владельцы остаются прежними: MW10 CrossRegionTransactionRepository и его
родственный MW9 DurableHandoffRepository. Coordinator, CAS/checkpoint,
pending-file protocol, сетевые каналы и gameplay authority не меняются.

Старый reclaim наблюдал протухшего A, затем переименовывал канонический
каталог в quarantine. Другой reclaimer мог уже удалить A, а живой B — занять
его место. Запоздавший rename перемещал B; свободный canonical path позволял
C войти одновременно с B. Проверка token после rename не закрывала окно.

## Исправление и аргумент безопасности

Acquisition по-прежнему публикует заранее заполненный каталог атомарным
rename. Его единственный owner-файл теперь называется `owner-<token>.json`;
token — 256 случайных бит от Crypto, не PID с переиспользуемым временем.

Release атомарно перемещает только собственный token-addressed файл в
уникальный released-файл. После удаления этого маркера владелец уже закончил
критическую секцию. Очистка канонического каталога — только `rmdir` пустого
каталога, никогда рекурсивное удаление файлов. Если B уже опубликовал новый
непустой каталог, очистка не может его удалить. Existing bounded release
retry и hook сохраняются. Ошибка, сообщённая после успешного rename,
распознаётся по собственному released-файлу, независимо от появления B.

Stale reclaim удаляет только точное имя файла наблюдавшегося A. Даже после
смены канонического каталога файл B имеет другое имя. Запоздавшая операция
над A не адресует B. Неоднозначный/повреждённый owner разрешает только
empty-only rmdir, но никогда удаление неизвестного файла. UNKNOWN liveness
не превращается в STOPPED только из-за истечения времени.

Сбой после перемещения owner-файла, но до rmdir оставляет пустой каталог;
reader устраняет его empty-only rmdir внутри прежнего bounded wait.

## Граница применимости и обновление

Это same-host lock для приватного локального filesystem и общего PID
namespace, а не распределённая блокировка сетевого хранилища. Нельзя
использовать /proc другой PID namespace как доказательство смерти владельца.

Все процессы-писатели MW9/MW10 должны быть остановлены и обновлены совместно.
Одновременное исполнение старых и новых writers запрещено: старый reclaimer
не понимает token-addressed marker. После остановки writers новая версия
может читать legacy `owner.json` и убирать подтверждённого протухшего владельца.
Не удалять неизвестные lock вручную во время работы writers. Повреждённый
непустой lock остаётся fail-closed; административное восстановление требует
подтверждённой остановки всех writers.

## Проверки

Новый обнаруживаемый тест `test_matter_repository_lock_reclaim.gd` наследует
настоящие классы repository. Acquire/release/reclaim не переписаны в тесте;
переопределены только точки планирования и controlled liveness.

Baseline: 22 assertions, ровно шесть ожидаемых failures (три на MW10 и три
на MW9). Candidate: 68 assertions, включая задержанного reclaimer,
неизвестного владельца, reported-error-after-move с уже вошедшим преемником,
неверный token, неоднозначный owner и прерванный release. Baseline parse error
или timeout не считается причинным negative control.

Дополнительно: прежние MW9 retry/process tests, MW10 processes, 5 EG1,
3 EG4, весь неизменённый world/core runner с независимым пересчётом discovery,
полный P7 train 29/2032 и весь Harness. Новый world/core должен обнаружить
новый тест; число стадий рассчитывается динамически, прежние 330 не являются
целевым ограничением. Исторические probes в docs не заменяют обычный gate.

## Контроллер и scope

Падение post-acceptance Harness вызвано fixture, неявно наследовавшим ACCEPTED
из main и ожидавшим отказ закрытия. Тест теперь явно строит ACCEPTED/PENDING
в отдельном disposable Git clone. Также проверяется, что незакоммиченная
подмена не меняет каноническое решение. Production controller не ослаблен.

`validate.py` фиксирует полный HEAD/TREE, clean tracked checkout до/после,
команды, exit codes, raw logs, SHA256 всех файлов. Он запрещает reuse старых
каталогов artifacts и не выдаёт verdict независимого Reviewer/Verifier.
Проверка PC0 относится к фактическому canonical main и помечается отдельно
от проверяемого кандидата. Исторический CloseMission=0 не принимает новый код.
