## Решение

Проверяемый продукт — неизменённый PR #814:

- PRODUCT_HEAD: `fdfbfb3b8dff911e6fd081a157652a28e1052cff`.
- PRODUCT_TREE: `585062871595267cbee4de38a1a8e41cec3a2605`.
- DIRECT_PARENT: `499c7fe7cb7958af0ae7a792316b2fa7e1c44a69`.
- BASELINE_ANCESTOR / база PR: `4e6840e23c6add8b61ecc818c023d19edd0d468e` (#809).

GitHub сравнение подтверждает ahead=10/behind=0 относительно #809. Различие между непосредственным родителем и базой PR ожидаемо для ветки из десяти коммитов; само по себе оно не доказывает rebase или нарушение тождественности.

Отчёт независимой Windows-проверки: PR #814, комментарий 6319272921. Все шесть серверных p99 26.3–28.3 мс выше нормы 25 мс; клиенты и M6 функционально проходят. Валидация p99 5.88/7.47/5.94 мс. **Автоматическое исключение валидации или кэширование результатов проверок сейчас не вводится.** Разные p99 нельзя вычитать или складывать, а несколько миллисекунд валидации всё ещё могут оказаться значимы именно в кадрах с checkpoint.

Два оставшихся после pair3 run-owned Godot-процесса означают, что B3 вновь открыт. Ранее подтверждённые успешные прогоны остаются фактами, но не доказывают надёжность очистки во всех ветвях. Причина утечки не установлена; новый сборщик ниже не объявляется исправлением.

## Объём этой вспомогательной ветки

Только два новых read-only инструмента, их синтетические тесты и инструкция. Игровой код, `owned_process_cleanup.py`, M6, валидаторы, частоты тика, `--max-fps 60`, нормативный анализатор и старые evidence не изменяются. Новая полная GUI-матрица на этом этапе не требуется.

### 1. Анализ server frame tail

`tools/net_smooth1/analyze_r31_server_tail.py` читает ровно три пары старых #814 OFF/ON. Проверяет HEAD/TREE, одинаковые wrapper/asset hashes во всех шести прогонах, обязательные флаги, полноту JSONL, sequence, dropped/io_errors, начало/конец измерения и длину окна. Сохраняет исходный нормативный verdict, ошибки и cleanup из manifest, SHA256 прочитанных файлов.

Для каждого измеренного frame сопоставляет **тот же локальный серверный clock** с событиями `server_loop` и реальными `checkpoint_capture`. Строит отдельные популяции кадров с checkpoint и без него, долю checkpoint в p99-tail и таблицу 100 самых длинных кадров. Не использует `server_loop.capture_ms` как текущую стоимость: это поле может хранить значение предыдущего checkpoint.

`frame interval - reported process_ms` называется **uncovered_probe_interval_ms**, а не «ожидание Windows». В него могут попадать frame limiter, другие callbacks, запись трассы, engine/OS-планирование, debug-отчёт и прочее. `server_loop.process_ms` не охватывает собственный последующий `SmoothTrace.emit()` и финальный SERVER_HEALTH. Это ограничение измерения, не установленная причина. Emit-timestamps не являются точными callback-границами: неоднозначные окна остаются UNRESOLVED и учитываются, а не исчезают.

`Performance.TIME_PROCESS` выводится только как monitor sample; он не принимается за гарантированное CPU-время текущего callback. Никакие монотонные часы разных процессов не объединяются. Значения условного p99 без checkpoint не заменяют исходный нормативный p99.

### 2. Независимая инвентаризация процессов

`tools/net_smooth1/capture_r31_process_inventory.py` сопоставляет wrapper PID из manifest с main-engine PID из trace header. В Windows трижды читает CIM: PID, parent PID, creation time, executable path, session, аргументы. Снимок включает все Godot-процессы и известные PID из evidence, поэтому не зависит только от старого exact-run-фильтра очистки. Значения automation-control-token маскируются **до записи**.

Инструмент **никого не завершает**. Совпадение PID может быть повторным использованием номера; наличие run marker не является разрешением kill. Для установления владельца нужны также время создания, executable и исходная команда. Уже убитые вручную процессы нельзя восстановить по последующей пустой таблице. B3 не закрывается текущим пустым inventory.

## Задание Windows-агенту: сначала повторное чтение, не очередные шесть запусков

1. Получить вспомогательную ветку в отдельный worktree. Не менять продукт #814 и старые JSONL. Записать TOOLING_HEAD отдельно от PRODUCT_HEAD.
2. Выполнить 22 Python-теста: `python -m unittest discover -s tests/tools -p "test_r31_*.py" -v`. Это тесты инструментов, не native M6-приёмка.
3. Найти шесть старых каталогов `artifacts/net-smooth1/r31bp20-gui/pair{1,2,3}-{off,on}` в `work\net-smooth-r31bp20-independent-20261022`. Не создавать новые прогоны только для анализа. Выходной каталог должен находиться вне evidence, а файл ещё не существовать.

```powershell
$Old = 'C:\ПУТЬ_К_WORKTREE\work\net-smooth-r31bp20-independent-20261022\artifacts\net-smooth1\r31bp20-gui'
$Out = 'C:\EVIDENCE\P21-tail-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
python tools/net_smooth1/analyze_r31_server_tail.py `
  --pair "$Old\pair1-off" "$Old\pair1-on" `
  --pair "$Old\pair2-off" "$Old\pair2-on" `
  --pair "$Old\pair3-off" "$Old\pair3-on" `
  --output "$Out\historical_tail.json"
```

4. Вернуть количество всех кадров/кадров >25 мс, долю capture в хвосте, p99 двух популяций, `reported_server_process_ms` и непокрытый интервал **в одних и тех же худших кадрах**, число UNRESOLVED. Не объявлять корреляцию причиной, не удалять длинные кадры, не усреднять p99 разных запусков в новый «общий норматив».
5. Для B3 сохранить оба pair3 manifest с оригинальными cleanup/errors, trace header PID, бывшие PID оставшихся процессов и команды до ручного kill, если они были записаны. Если creation time/command line не сохранены — отметить доказательства как недостающие, не придумывать причину.
6. Независимый текущий read-only inventory можно снять так:

```powershell
python tools/net_smooth1/capture_r31_process_inventory.py `
  --run-root "$Old\pair3-off" --run-root "$Old\pair3-on" `
  --godot-console 'C:\Godot\godot\bin\godot.windows.editor.double.x86_64.console.exe' `
  --godot-main 'C:\Godot\godot\bin\godot.windows.editor.double.x86_64.exe' `
  --output "$Out\process_inventory.json"
```

В нём отдельно фиксируются SHA обоих EXE. Расхождение старого wrapper SHA `457de516…` (#809) и `3633c3e6…` (#814) не закрывается очередным совпадением версии. Main SHA `6464da35…` — наблюдение, не независимый эталон.

7. Только если старых B3-артефактов недостаточно, один короткий контролируемый прогон для воспроизведения очистки; inventory до/после, не убивать чужие процессы. Исходный краткий тест не заменяет нормативные 120 секунд и не закрывает B3 без воспроизведения сбоя/отрицательных тестов. Никакой новой полной матрицы до разбора этих результатов.

## Следующее решение по результатам

Если медленные кадры действительно содержат длинный capture/main-thread work — выбирать конкретный измеренный участок (включая валидацию при подтверждении). Если доминирует непокрытый интервал — провести отдельный эксперимент по frame cadence/лимитеру/планированию, сохраняя authoritative fixed simulation 60 Гц и нормативы. Не повышать FPS cap или приоритет скрыто ради зелёного p99. Для B3 изоляция процесса должна подтверждаться идентичностью и временем создания; при необходимости отдельная реализация Windows Job Object с native тестом потомков после выхода wrapper (не реализована этим пакетом).

Normative: server и оба клиента p99≤25 мс, p99.9≤50 мс, max≤100 мс, sim≥59 Гц. Issue #815, Project Control, P7.4 и SEAM-E2E остаются отдельными открытыми условиями. **NO_MERGE.**
