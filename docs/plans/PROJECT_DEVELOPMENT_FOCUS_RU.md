# Фокус развития проекта

Срез: 5 сентября 2026. База анализа: `5b4152958624be4e9cc40f2369ce32c4964f65c3`.
План становится текущим после принятия control-изменения в main. До этого он является предложением в отдельной ветке.

## Главный результат

Ближайшая цель — работающее визуальное сетевое MVP: два клиента в одном изменяемом мире, бесшовный переход между authority, сохранение изменений и предметов. Исследовательские результаты должны помогать этой цели, но не расширять её обязательный объём.

Основа развивается последовательно: P7 собирает готовых владельцев Matter, Item Graph, persistence и networking. Главная обнаруженная проблема — расхождение результатов веток с центральным маршрутом работы. Обзор ещё направлял на P7.2, goals — на pre-dispatch P7, scheduler — на реализацию P7.7, хотя runtime PR #487 уже merged. Исправление — единый текущий маршрут и явная степень подтверждения результатов.

Цели находятся в `project-goals.v1.json → lane_goals`; наблюдаемое состояние и точные commits — в существующем `project-program-registry.v1.json → coordination`. Это описание семейств работ, не второй scheduler и не новые владельцы foundations. Разрешение исполнения остаётся за catalog, main-owned activation, Work Order, Director и единственным runtime lease.

## Последовательность MVP

| Шаг | Конкретный результат | Условие перехода |
| --- | --- | --- |
| 1. Сверка закрытия P7 | Связаны существующие review, verification, merge, post-merge PC0 и итоговая acceptance | Сначала найти уже полученные доказательства; merge не заменяет приёмку |
| 2. Активация MVP composition | Точная принятая база, свежий epoch, ограниченный Work Order, согласованный lease | P7 ACCEPTED в main и принятая активация преемника |
| 3. Общая визуальная сцена | Понятные вход, управление, отображение клиентов, инструмента и изменяемой поверхности | Используются принятые P7/SM1 компоненты без нового terrain/network/item store |
| 4. Совместная работа | Два клиента видят копание и материал; A→B→A сохраняет сессию | Один эффект/одна выдача, согласование клиентов, без штатного reconnect/respawn |
| 5. Восстановление и приёмка | Изменения сохраняются после reconnect/restart; понятный запуск и бюджет ресурсов | Проверенная общая композиция, независимые review/verification и необходимые human gates |

Идентификатор результата: `V0_PLAYABLE_SEAMLESS_PLANET_COMPOSITION_ACCEPTANCE`. Он объявлен как планируемый checkpoint, а не dispatched implementation. Его planner/activation входит в ограниченный Work Order шага 2.

P7.7 уже содержит графический Digging Playground. Визуализацию не нужно начинать с нуля: необходимо собрать существующие части в один пользовательский сценарий. Отдельный лабораторный PASS не доказывает приёмку всей композиции.

Сохранённое rotation evidence P7.7 сообщает `MERGED_BUT_NOT_CLOSED; COMPLETE_MERGED NOT DECLARED`, хотя чат сообщал о закрытии. Это расхождение доказательств, а не установленная runtime-поломка. Пока каноническая итоговая запись не найдена, controller направляет Director на сверку. При появлении P7 ACCEPTED завершённую P7 mission можно закрыть; активация MVP остаётся отдельным следующим действием.

Не требуются для первого MVP: LS4 FINAL, FABRIC B0.6, полный WORLDGEN1, RF1, P8 и все WORLD PACKS. Реальная зависимость оформляется отдельно с конкретным потребителем и критериями. Исследовательская ошибка сама по себе не останавливает MVP.

## Экология: один экспериментальный полигон

Цель — участок среды, совместимый по смыслу с детальным уровнем планеты, где можно менять условия, наблюдать наследование и поколения, сравнивать сценарии и видеть причинное разнообразие растений.

LS3.6 даёт rule workbench; LS4.1 добавляет несколько видов и наблюдатель; VIS5.5 подготовил terrain/ecosystem presentation handoff. Registry связывает их с PERF2.CONV integration и first-frame repair по точным commits.

Ограничения текущего среза:

- LS4.1 и LS4-VIS1 заявлены как IMPLEMENTED с ожидающей exact runtime-проверкой. Это ещё не закрытие цели полигона.
- Три вида на общем участке в LS4.1 пока представлены отдельными LS3 cores. Межвидовые эффекты и общий ресурсный бюджет относятся к следующим LS4.2/LS4.3.
- PLAY1 используется и для PERF2.CONV + VIS5.5 integration, и для будущего Living Ecosystem Region после LS4. Это разные результаты.
- Зрелищность и разные цвета не доказывают генетическое разнообразие. Нужна связь формы с фактическими наследуемыми признаками и условиями.

Ближайший результат — один формат экспериментальной сессии и один владелец состояния. Вход: seed, среда, каталог, правила наследования. Управление: pause, шаг поколения, скорость, reset, сравнение одинаковых исходных условий. Выход: поколение, выбранная особь/когорта, genotype/phenotype, метрики разнообразия и ограниченный журнал изменений. VIS читает этот снимок; анимация и LOD не меняют биологическое состояние.

Далее сохраняется LS4: species → interactions → resources → trophic → disturbance → succession → engineering → feedback. Каждый шаг должен добавлять наблюдаемый причинный опыт в общей сессии. Полезный лабораторный интерфейс нужен до завершения всей биосферы.

Передача в основной симулятор — позже через явный consumer contract: версионированные рецепты/каталоги с seed, environment/rules/catalog hashes, областью применимости и происхождением результата. Живая память research-процесса не становится вторым world state. Точные поля контракта утверждаются отдельной работой; здесь фиксируются требования.

## FABRIC: физика, запекание и наблюдатель

Цель — получить сложное поведение из общих деталей и связей и сохранить причинность при более дешёвом представлении внутренностей.

Семейство: CORE `FABRIC0.18`, BAKE `B0.6`, наблюдатель `COMPLEX2`. Старый B0.5-A/BRIDGE-2 остаётся источником доказательств. Свежий commit старой ветки не делает её новым основным направлением BAKE.

Сильная сторона — лестница примеров: разрушение, разрыв питания, резервный путь, смешанные представления, пружинная реакция, rebake и повторный удар. Уточнить нужно границы доказанного:

- В изученном COMPLEX2 backend FULL и compiled используют одинаковые восемь состояний и общий интегратор. Кэширование матриц полезно, но не уменьшает число динамических состояний. Это не отменяет отдельные доказательства B0.4 Dynamic ROM.
- Варианты 500/1000/2000 деталей используют те же 25 модулей. Это масштаб выбранного стенда, а не общность решателя для неизвестной машины.
- Сравнение режимов на общей вычислительной основе нуждается в дополнительном физическом ориентире: одинаковая ошибка может выглядеть как согласие.

Следующие шаги: разобрать заявленный B0.6-A admissibility envelope → завершить B0.6 adaptive fidelity → BRIDGE-3 FULL/BAKE/UNBAKE/FULL → COMPLEX3 → B0.7 unseen-machine. В B0.6/BRIDGE-3 зафиксировать допустимую ошибку, стоимость fallback, локальность unbake, сохранение портов и порядок invalidation/rebuild. Численные пороги выбирает соответствующий research Work Order.

Обсерватория показывает те же physical snapshot/events, режим представления, причину unbake и восстановление связей, что использует эксперимент. Сценарный обработчик «погасить лампу после удара» не заменяет событие в реальной цепи питания. FABRIC0.19 открывать только при конкретном примере, которому не хватает общего примитива.

## Поддержание порядка

1. Перед выбором задачи обновить нужные Git refs и прочитать `CONTROL_DEVELOPMENT.ps1 -Overview`. Команда сама не делает fetch и сообщает ограничение наблюдения.
2. `-CheckConsistency` проверяет продуктовый контроль; локальные проблемы ECO/FABRIC остаются видимыми findings своего семейства и не превращаются в неявный MVP gate.
3. Зафиксировать одну цель, точную базу, ожидаемый наблюдаемый результат и ответственного. Рекомендация обзора не заменяет Work Order.
4. После этапа обновить pin и source-report в registry вместе с оперативными policy-полями. Продвижение ветки требует прочитать новые доказательства, а не автоматически повысить статус.
5. Не копировать текущий следующий шаг в независимые roadmaps. Этот план описывает последовательность; CURRENT_PROJECT_FRONTIERS только направляет в machine-owned обзор.
6. Исторические acceptance, epochs, review и logs сохранять. Новый registry generation требует явной сверки epoch, а не массовой правки старых свидетельств.

WORLD FILL и WORLD PACKS — отключаемые поставщики оформления. Контент не получает собственных владельцев Matter, Item Graph, networking или persistence. В MVP переносить ограниченные элементы, помогающие читать происходящее в общей сцене.
